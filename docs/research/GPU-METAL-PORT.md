# Porting UniXNU Adreno740 + AdrenoMetal (sheng, Metal verified) to ruan's A710

Research 2026-11-17 (read-only). Core = /root/unixnu-work/UniXNU, S = UniXNU/UniXNU-sheng, R = UniXNU-ruan.

Key findings
- Pinned Mesa 85fda3b has no FD710; Mesa main freedreno_devices.py:965-1082 has it (chip 0x07010000, a7xx_gen1, 1 CCU, hbb 15, a710_raw_magic_regs) -> backport patch.
- sheng's iPadOS 17.7.11 override already builds Adreno740 + AdrenoMetal + AirNir (S board.toml:175-192); Community Adreno830 (SM8750) is the model for a non-A740 fork (docs/drivers/community-adreno830.md).
- Real path is board code (S package/GpuPowerProbe.cpp): power, hw_init, CP init, native_adreno_publish(...), publishMetal() (IOAcceleratorES subclass, MetalPluginName=NativeAdrenoMetal).

ruan values: chip 0x07010000; GMEM 512 KiB; hbb 15; UBWC 4 (swizzle/macrotile: read KGSL gen7_3_0, start with noubwc); hwcg/protect from RuanA710HwInit.h; gmu_gen70000.bin / a710_sqe.fw / a710_zap (PAS 13); GPU SPI 300; GMU 0x3d68000 (core delta 0x68000, not 0x6a000), IRQs 304/305; cmd-db 0x80860000; pwrlevels 940..295 MHz in live DT; no preemption/IFPC/ACD (gpu-preempt=0); GPU SMMU bank 2 SID 0 mask 0x400, GMU bank 1 SID 5; 16 MiB pool 0x8B8B00000.

Risks: ArmSmmu4K kit has no SMR mask and wants two routes (small patch); never call ArmSmmu4KDisableOwnedContext (Gunyah SEA); SCM CP aperture is for cb 0, ruan GPU is bank 2; Turnip/metal2vulkan tuned on a7xx_gen2 (A710 gen1, 1 CCU) -> TU_DEBUG=sysmem first, no shader cache reuse; --target ios path may have bit-rotted; arm64 only; Turnip/plugin need macOS xcrun + iOS SDK; driver includes ShengGmu.h (point at sm8550 kit headers, skip ShengGmuColdStart, keep ruan's GMU boot).

Steps (each testable)
1. Host: Mesa FD710 backport patch; build-turnip-darwin.py --target ios; ir3 compile for FD710.
2. Device: RuanAdrenoGlue.cpp after ruan GX-on: NativeAdrenoGpuContextBringup (bank 2, SID 0/mask 0x400, pool buffers), NativeAdrenoCpInit with A710 pwrup list, one CP_MEM_WRITE via NativeAdrenoRing -> fence over USB.
3. Device: native_adreno_publish with gDeviceInfo {0x07010000, 512K, 0x1000000, 0x1fffffffff000, ..., hbb 15, swz 6?, macro 0?, ubwc 4}, gpu-preempt=0, SPI 300 -> native_adreno_gpu_interrupt; test gpu-selftest=1.
4. Device: Turnip smoke (Vulkan clear readback) with tu-debug=sysmem,noubwc.
5. Device: AdrenoMetal plugin --target ios, gpu-metal=1 gpu-addon=1, publishMetal(); CPU display copy kept.
6. Then fb-gpu, GMEM, UBWC, zap, DCVS.

## Note from Vauzi-17/710 (Turnip builds tuned for A710 on Android, checked 2026-11-17)
- Upstream Mesa `main` Turnip runs on A710 hardware; their recommended stable baseline is `TU_DEBUG=sysmem` (no GMEM binning). Use `TU_DEBUG=sysmem` for our first Turnip smoke test (step 4), then try GMEM.

- Diagnosis caveat: in `wc4 uc1 wc1` what fails is "every run after the first", whatever its map mode. Between runs the test frees both BOs and maps new ones at the same two GPU addresses (va_start, +0x1000); with the pool, the freed (viewed) pages do not come back, so the new BOs have new physical pages. Only the translation (or a GPU-side cache keyed by GPU address) can serve the old page. That is not proven: a GPU cache keyed by address (UCHE) would look the same.
- rbu48a (`gpu-tlbiall=2`): raw ABI test passes (`V wc4 uc4 wc4`). Turnip `T s0 r0 v512 c0 g0/4096`: no Vulkan error, but nothing Turnip's GPU work writes reaches memory. v512 = only the untouched half of the fill buffer (still 0xdeadbeef) is right, c0 = no compute word, g0/4096 = no clear or triangle pixel. CP_MEM_WRITE (the raw test) bypasses UCHE; fills, shaders and blits all go through UCHE/CCU. The open line `macf 0 res e00002c7 type 4147` is the smoke tool's own open: the sandbox allowed it, and the resolver had no filter policy (Unsupported). Harmless.
- Cause: RuanA710Regs.h had a5xx offsets for UCHE (TRAP/WRITE_THRU at 0xe83..0xe88, cache ways at 0xe85), CP_AHB_CNTL (0x840) and RBBM_GBIF_HALT (0xa), so UCHE was never configured. UCHE_GMEM_RANGE, CMDQ_CONFIG, CLIENT_PF, the NC_MODE registers and UCHE_MODE_CNTL were never written either.
- rbu49 (built, not booted): gen7 offsets (KGSL gen7_reg.h) plus gen7_start's UCHE/NC_MODE writes; GMEM range 16 MiB + 512 KiB, matching the gmem_base reported to Turnip. `gpu-tlbiall` defaults to 2 (0/1 override). Root = rbu46's.
- rbu49: unchanged (`wc4 uc4 wc4`, `T s0 r0 v512 c0 g0/4096`). Process tables do work: the raw test's IB and target are process VAs (va_start) on the switched TTBR0 and pass. So "CP stays on the kernel context" doesn't fit; the failure is specific to what Turnip's IBs do.
- rbu50 (built, not booted; boot args + `diag=1`): `gpu` adds `[usb] REGS` (RBBM_INT_0_STATUS/STATUS/STATUS3, CP_HW_FAULT, CP_INTERRUPT_STATUS, CP_PROTECT_STATUS, BV fault/protect, RB rptr/wptr, IB1/IB2 base and remaining size, UCHE write-thru/GMEM min/ways readback, CB2 FSR/FAR/FSYNR0/TTBR0), `[usb] SUBMIT` (submissions/IBs, table switches by CP/CPU, fence-wait counters: calls, timeouts, last timed-out fence and the GPU's value, newest issued/completed), the last 4 `[usb] IB` (fence, iova, bytes, first 8 dwords; diag=1 now set by RuanAdrenoGlue.cpp), the last 2 `[usb] RING` packets and `[usb] STALLFAULT`.
- rbu50 (`gpu-rbu50.txt`): the GPU ran Turnip's work completely. 6 submits, fences all completed (no wait timeouts), rptr = wptr, IB1/IB2 remaining 0. No GPU interrupt, HW fault or protect fault; CB2 FSR shows only its format bits, no fault; the CPU switched TTBR0 for each process (3 made and freed). The ring framing is a7xx_submit's (CACHE_FLUSH7/INVALIDATE7 before, CCU invalidate + CACHE_CLEAN fence after). Yet every UCHE/CCU write is lost, while CP_MEM_WRITE (no UCHE) lands. The hw_init writes of UCHE_GMEM_RANGE_MIN (0x1000000) and CACHE_WAYS (0x800000) read back 0 and 0x40004: those registers did not take the HLOS write.
- rbu51 (built, not booted): `gpu` REGS adds gmax/umode/pf and GR0 sGFSR/sGFSYNR0..2 (global faults: a GPU stream no SMR routes is dropped silently there; sGFSYNR1 low 16 bits = its SID) plus SMR/S2CR slot 1. Two gates: `gpu-smr-mask=0x401` (route SID 1 too, as sm8250/sm8550 give the GPU SIDs 0 and 1) and `gpu-gmem-base=0x100000` (KGSL's gen7 UCHE GMEM base, for both UCHE_GMEM_RANGE and what Turnip is told). Images: out-rbu51 (defaults, diag=1), out-rbu51s (+smr mask 0x401), out-rbu51g (+gmem base 0x100000).
- rbu51 reset during boot: its replay ends at 158.3, in launchd's quiet first minute and before any `gpu` query. The GR0 reads run only on a query, so they are probably not the cause (rbu47's TLBIALL is likewise unproven). They are still off now unless `gpu-tlbiall`-style `gpu-gfsr=1`.
- `gpu-gmem-base=0x100000` (KGSL's value) is unsafe here: the driver's fixed kernel IOVAs start at 0x100000 (SQE 0x100000, ring 0x200000, memptrs 0x300000), so the GMEM window would cover the SQE. Default stays 16 MiB; out-rbu51g has it and must not be booted.

Root = rbu54's.
- rbu55: unchanged (nothing written). - rbu56: Turnip's IBs are in memory and valid (CP_THREAD_CONTROL, CCU/cache events, HLSQ_INVALIDATE_CMD, RB_CCU_CNTL, UCHE_CACHE_WAYS 0x40004 from the IB, which reads back, so IB register writes take). REGS show RBBM_SECVID_TRUST_CNTL = 1: the GPU never left secure mode. ruan's "secure mode exit" stage (s3_zap, gpu 12) only reads the register. KGSL gen7 without a zap shader writes TRUST_CNTL 0 (adreno_gen7.c gen7_rb_start); with one it sends CP_SET_SECURE_MODE 0. In secure mode the 3D/2D/UCHE traffic is plausibly tagged secure (gfx3d_secure is SID 2, mask 0x400), which no SMR here routes, so it is dropped without a CB2 fault; CP_MEM_WRITE lands.
- rbu57 (built, not booted, root = rbu54's): `gpu-trust0=1` writes RBBM_SECVID_TRUST_CNTL 0 in s3_glue right after hw_init (before CP init), with boot-progress events `gpu trust0: writing...` and `gpu trust0: <before>><after>[ refused]` around it, since a secure-world lock could make the write fatal. Without the argument nothing changes.
- rbu57: the HLOS write of RBBM_SECVID_TRUST_CNTL took a synchronous external abort (esr 0x96000010, pc in ruan_gpu_run `str wzr, [x8, #0x3d000]`). The register is secure-locked, which fits the secure-mode theory. The write path is removed (REGS still reads trust=). Note: gpu-metal-turnip-roadmap.md's "zap authenticated via PAS 13" was never true on ruan; s3_zap only read the register.
- rbu58 (built, not booted, root = rbu54's): `gpu-zap=1` runs RuanAdrenoGlue.cpp zapExit() once after CP init, before publish. It is amethyst's mode 15 (GpuPowerBoard.h helpers and AmethystSmc.c copied into package/RuanZap.h) on ruan's values: SCM is_call_avail → PAS is_supported(13) → a710_zap.mbn parsed (array generated by build-ruan-adreno.py from the vendor firmware, never committed) → metadata in one contiguous page (ruan has no RAM below 4 GiB, so no 4 GiB mask) → init_image → mem_setup on gpu_microcode_region 0x89e1a000+0x2000 → load segments written through a write-combined map → auth_and_reset → CP_SET_SECURE_MODE 0 + CP_MEM_WRITE 0x05ec0ff1 from the ring. Each step is a boot-progress event (`zap scm <call> …` / `-> st … val …`, `zap: secure off … trust <x> -> ok|miss`). Without the argument nothing changes.
- rbu58: `is_call_avail` (0x42000601, arg 0x2000207) → st 0 val 1; `is_supported(13)` (0x42000207, arginfo 1, x2 = 13) → st 0 val 0. That is the same call Linux qcom_scm_pas_supported makes (SMCCC 64-bit SiP std call, owner 2, result in x1), so it is a real "no", not a malformed call. amethyst's A810 got "supported" (WORKING-BOOT.md:366). trust stayed 1.
- rbu59a (built, not booted): `gpu-zap=2` = rbu58 but goes on past is_supported 0 (init_image / mem_setup / auth_and_reset, each status logged).
- rbu59b (built, not booted): no zap; `gpu-smr-mask=0x402` (existing argument, same slot-1 SMR write as gpu 17) routes SIDs 0, 2, 0x400, 0x402 to bank 2, so secure-tagged gfx traffic (gfx3d_secure is SID 2) would land in our table. Same kernel as rbu59a, root = rbu54's.

## Checkpoint rbu44–rbu60 (2026-11-17)
- Works: Turnip (Mesa + FD710 = main's entry) for iOS built on Linux; smoke tool as /usr/bin/IOMFB_FDR_Loader with an owner trust module; accelerator opens go to the real driver; `ruan-gpu=18` at boot; raw ABI test `V wc4 uc4 wc4` once every map/unmap clears the bank's TLB by ASID (`gpu-tlbiall=2`, default since rbu48a); gen7 UCHE offsets fixed (a5xx ones before rbu49); diagnostics in `gpu` (REGS, SUBMIT, IB/RING words via a DRAM reader with diag=1, TEXT, D line).
- Turnip: no Vulkan error, the GPU consumes every IB and faults nowhere, but no RB/2D/SP/UCHE write lands (`D fdeadbeef… cdeadbeef r5a5a5a5a`). REGS: RBBM_SECVID_TRUST_CNTL = 1 → the GPU is in secure mode. CP_MEM_WRITE from the ring lands.
- Dead ends: HLOS write of TRUST_CNTL → SEA (rbu57); SMR mask 0x402 (route SID 2) → SEA (rbu59b, Gunyah refuses); GMEM base 0x100000 overlaps the SQE IOVA; GR0 reads are only safe gated (`gpu-gfsr=1`, off).
- Zap: SCM is_call_avail ok, PAS is_supported(13) = 0 (rbu58, same call as Linux). rbu59a (`gpu-zap=2`, past is_supported, metadata in a kernel page above 4 GiB) resets deterministically, before any zap event reached ramoops.
- KGSL (parrot 5.15, OnePlus sm8475 tree): kgsl_zap_shader_load never calls is_supported; qcom_mdt_load(pas 13) puts the metadata in dma_alloc_coherent memory ("XPU-protected during the call, so contiguous, 4K aligned, non-cacheable"), then init_image, mem_setup, segments through memremap WC, auth_and_reset. This SoC's DT has qtee_shmbridge: TZ may require buffers passed to it to be in a registered SHM bridge (qcom_scm_create_shm_bridge), which our pages are not. That is the next suspect if init_image itself resets.
- rbu60 (built, not booted; root = rbu54's, all with diag=1): rbu60a `gpu-zap=3` (kernel page metadata, stop after init_image); rbu60b `gpu-zap=5` (metadata in ramoops dmesg record 0 at 0x80D00000, below 4 GiB, uncached; stop after init_image); rbu60c `gpu-zap=6` (low metadata, init_image + mem_setup, no segment writes); rbu60d `gpu-zap=4` (low metadata, full). Each zap event is followed by a 20 ms pause; ramoops writes were already synchronous (device mapping + dsb sy per line), so a missing line means the reset came before it ran.
- Intermittent (≈1 in 3) silent resets right after launchd exist independently of these changes (rbu51/52 reruns, rbu53).
- rbu60: the is_supported check still read `zapMode != 2`, so modes 3–6 (and rbu60d's 4) stopped there and never ran init_image. rbu60d's reset was therefore not the zap; count it with the ≈1/3 flaky resets. Only rbu59a (mode 2, kernel-page metadata, full sequence) has run past is_supported, and it reset.
- rbu61 (built, not booted; root = rbu54's): the check is fixed (`< 2`). rbu61a `gpu-zap=3`, rbu61b `=5`, rbu61c `=6` as rbu60. rbu61e `gpu-zap=7`: low metadata + SHM bridge for it (SCM MP 0x0c/0x1e as downstream qtee_shmbridge_register without qcom,support-hypervisor: paddr|6, paddr|6, 0x1000|1<<9, VMID_HLOS 3), then init_image only.
