# ruan Adreno 710 bring-up (staged, not merged)

GPU acceleration track for ruan (SM7435 "parrot", Adreno 710 = KGSL gen7_3_0, chip 0x07010000, under Gunyah). Everything here
is staged: nothing is in UniXNU-ruan yet, nothing has run on the tablet. Model: amethyst's Adreno 810 path under Gunyah
(`refs/UniXNU-amethyst/scripts/log/WORKING-BOOT.md:297-429`). Feasibility: `gpu-prep/adreno/PLAN.md`.

## Sources (every value cites one)

- `src-ref/` holds verbatim copies of `OnePlusOSS/android_kernel_oneplus_sm8475` @ `7278ce9a3c8539b4630d6988cc80f90c31c07336`
  (an official OEM kernel for an SM8475 phone that also carries the parrot drivers), see `src-ref/SOURCES.txt`:
  - `drivers/clk/qcom/gcc-parrot.c`, `gpucc-parrot.c`, `include/dt-bindings/clock/qcom,{gcc,gpucc}-parrot.h`;
  - KGSL `drivers/gpu/msm/`: `adreno-gpulist.h` (`adreno_gpu_core_gen7_3_0`), `gen7_reg.h`, `adreno_gen7*.c/h`,
    `kgsl_gmu_core.h`.
- The live DT: `macOS/hardware/private/ruan-live.dts`.
- Firmware: `work/analysis-vendor/stock/vendor_a/firmware/` (names and hashes only, never committed).

Key facts:
- **A710 = A730 (gen7_0_0) minus IFPC, ACD and preemption.** Same GMU firmware (`gmu_gen70000.bin`) and same protect list. It differs in gmem (512 KiB), highest_bank_bit (15), hwcg (no BV_* entries) and GBIF QoS (3, not 0x2120212).
- **Parrot GCC and GPUCC offsets differ from amethyst's volcano:**
  - GCC GPU branches sit at 0x81000, not 0x71000; the GPLL0 vote at 0x62000.
  - CX GDSC is at 0x9108, with hw-ctrl at 0x953c; gpu_cc_ahb at 0x911c.
- **The GMU runs at 200 MHz and the hub at 150 MHz, both from GPLL0_OUT_MAIN_DIV.** No GPU PLL is needed to boot the GMU. amethyst needed PLL0.
- **The DT's GMU window (0x3d68000+0x37000) overlaps GPUCC and CX_MISC.** GMU-stage writes must be allowlisted by register.

## What to read on the device

**Boot page** (before the hand-off):
- `gpu: touching <window>` is printed before each first access. If the boot stops right after one of these lines, that block hung the bus.
- `gpu m<mode> gcc ok ahb <before>><after> memnoc .. dvm .. axi .. vote .. w<writes> e<io_error>`
- `gpu cc <ok|skip> cx <GDSCR> hw <hw-ctrl> gx <GDSCR> ahbclk .. smmuclk .. gmuclk ..`
- mode 3 adds:
  - `gpu cx-up before .. init .. after .. tries N refused R cx 1 clocks 1`
  - `gpu smmu ok scr0 .. id0 .. id1 .. id2 .. gfsr .. smr N valid V`

**Banner** (after the hand-off):
- The second input row starts with `gpu m<mode> cx<on|off> gx<on|off> smmu<ok|->`.
- In the full banner (`boot-progress-banner=1`), the reason row shows the last `gpu cc …` or `gpu smmu …` line while no abort reason is shown.

**Pass criteria:**
- **m1:** `gcc ok`, plus either `cc ok` or `cc skip` (skip just means cfg_ahb is off).
- **m2:** `ahb` shows bit 0 set after the write, and `cc ok`.
- **m3:** `cx 1 clocks 1` and `smmu ok`. For S2, also read how many SMRs are already valid (Gunyah may own some) and ID0/ID1, which give the bank layout.

## Userspace (S5) plan

- **Pieces:** UniXNU `drivers/AdrenoMetal` plus Turnip (pinned Mesa has FD710, chip 0x07010000; `turnip-darwin-kmd.patch` derives 710 with no special case).

- **Two routes:**
  1. a GitHub Actions macOS runner, as amethyst used (AM:376, 425-428). This is the proven one.
  2. the host's `/root/theos/sdks-git/iPhoneOS16.5.sdk` with the Linux clang/ld64 in `/opt/unixnu-linux`. Untested; the plugin targets iOS 17 and links Metal and IOSurface, so a 16.5 SDK may lack symbols.
- **Delivery:** the add-on goes in through `/chosen/memory-map/GpuAddon` (`native_ram_block_gpu_addon`, already in our kernel). It is not needed before S4.

## Risks

- **Mode 3 makes real writes to GPUCC power control.** A wrong GDSC sequence can hang the bus or power-collapse something. The sequence and the values are the downstream driver's, the DT's and amethyst's (proven on a 7-series chip under Gunyah), and the boot is RAM-only.
- **gcc_gpu_cfg_ahb may already be on.** Linux forces it at GCC probe, so mode 2 often writes nothing.
- **Gunyah may own GPU SMMU streams or refuse GPUCC writes.** Mode 3's SMR survey shows which streams are already claimed; a refused write shows as `e1` or `cx 0`.
- **KGSL version:** the A710 hwcg, gbif and protect values come from one KGSL version (5.10, SM8475 tree). Mainline's a730_protect splits the 0x8d0-0xa40 span differently from index 9 on. If S3 faults on a protected register, compare against the ruan stock kernel's KGSL (Xiaomi MiCode ruan source) before trusting either.
- **Zap carveout:** 8 KiB (0x89e1a000) holds the zap's two segments (5844 bytes), but PAS 13 under Gunyah on ruan is unproven.
- **Time:** S2–S5 are still weeks of work (see `gpu-prep/adreno/PLAN.md`).

## rb18g3 crash and the USB-driven g3 (rbu3b, 2026-11-14)

- **What happened:**

  - **rb18g3 (mode 3 at boot) reset the tablet.** RAM didn't survive, so the failing step is unknown.
- **rbu3b** (kernel `aed7aff7`, image `a1b8275a`, rbu's args, no `ruan-gpu`, root from rb18) runs S1 only on the USB debug link's command. The USB side lives in `usb-dev/package/UsbDebugGpu.h`; `usb-dev/tools/ruan_additions.py` inserts its include and three hooks into the generated `UsbDebugCdc.cpp`, so it survives a regeneration from j716f:
  - `gpu` prints the last result; `gpu 1`, `gpu 2` or `gpu 3` queues that mode. The USB thread's main loop runs it, outside `pollUsbEvents`.
  - Every register access is preceded by a `GPU rd <window>+<off> <name>` or `GPU WR <window>+<off> <name> <- <value>` line, sent with `usbFlush` (EP3 XFERCOMPLETE) before the access. Each read's value follows as `GPU    = xxxxxxxx`, and each write is followed by `GPU    written` after `dsb sy`.
  - **The last line zima received names the access that hung or reset.** If the host stops reading, the access is skipped and counted as an I/O error.
- Sequence order (mode 3):
  1. GCC reads, then GPUCC reads;
  2. `WR cx_gdscr` (config: HW_CONTROL and SW_OVERRIDE off, CLK_DIS_WAIT 8), then read back;
  3. `WR cx_gdscr` (SW_COLLAPSE clear);
  4. the `rd cx_gds_hw_ctrl` poll;
  5. `WR cx_gdscr` (RETAIN_FF), then read back;
  6. `rd/WR gpu_cc_ahb`, then `rd/WR hlos1_vote_gpu_smmu` and its poll;
  7. the gate reads (`cx_gmu`, `hub_cx_int`, `gpu_snoc_dvm_gfx`);
  8. only if all three run: `rd SMMU+…`.

## g3 passed over USB; S2a (rbu4)

g3 result (USB command, after boot):
- **CX:** `cx f8228800`, `hw 80001fe0` (PWR_ON); the poll succeeded on try 1. `smmuclk 00000001`.
- **SMMU gate passed:** `gmu 00000221`, `hub 00000001`, `dvm 00000001`.
- **SMMU:** `scr0 00210406 id0 4c017e18 id1 40000016`, 24 SMRs, none valid. The hypervisor owns no GPU streams, so the GPU and GMU banks are ours.
- **`gpu_cc_ahb` reads 0 after the enable write, with CLK_OFF 0.** The branch is running (the SMMU reads needed it), and the SW enable bit doesn't latch. It's probably voted or hardware-controlled on parrot. Harmless; treat CLK_OFF=0 as "on".

Why the boot-time g3 reset but the USB run didn't (most likely: timing):
- **At boot:** the sequence ran flat out. The SMMU global space was read microseconds after the CX GDSC reported PWR_ON and the vote clock started. Right after power-up the TCU/SMMU is still coming out of reset and initialising its memories, and an access in that window can stall the bus until the NoC times out, which resets the SoC.
- **Over USB:** every access waited for a USB round trip, so milliseconds passed between steps.
- **Other boot-time factors were present but can't be separated:** `ruan-cpufreq` started its vote thread just before, and display/IOSurface bring-up and the first frame copies ran concurrently.
- **Conclusion:** S2+ stays USB-command only (`ruan_gpu_survey` refuses `ruan-gpu` above 3 at boot). Any future boot-time use needs explicit settle delays after each power-domain and clock change.

**S2a = `gpu 4`** (USB only). It reruns the g3 gate first (if CX is already on it only re-reads), then:
1. GCC GPLL0 GPU votes (0x62000 bits 15/16), only the missing bits, with a 10 µs halt delay;
2. `gpu_cc_gmu_clk_src` to 200 MHz (CFG `0x0602`) and `gpu_cc_hub_clk_src` to 150 MHz (`0x0603`), both from GPLL0_OUT_MAIN_DIV, with the clk_rcg2_shared sequence:
   - set ROOT_EN and wait for ROOT_OFF to clear;
   - write CFG (mask 0x371f), then CMD_UPDATE, and wait for it to clear;
   - drop the forced ROOT_EN;
3. branches `cx_gmu` (bit 0 plus gpucc-parrot's 0xF0 staggering bits), `cxo`, `hub_cx_int` and `hub_aon`, each polled for CLK_OFF to clear;
4. only if cx_gmu, cxo and hub run: map the GMU (0x3d68000) and RSCC (0x3d50000) windows and READ:
   - from the GMU: CM3_SYSRESET, BOOT_CONFIG, FW_INIT_RESULT, CM3_CFG, HFI_CTRL_STATUS, RPMH_POWER_STATE, AO_HOST_INTERRUPT_STATUS, AO_GPU_CX_BUSY_STATUS, RSCC_CONTROL_ACK and the AO counter;
   - from the RSCC: RSC_STATUS0_DRV0 and SEQ_BUSY_DRV0.
   - Offsets are KGSL gen7_reg.h dwords from the GPU base. **Nothing in the GMU or RSCC is written; the GMU stays in reset.**

**`gpu off`** reverts, in reverse order, only what gpu 3/4 turned on (tracked in `owned`): GMU branches, RCG CFGs back to their old values, GPLL0 vote bits, the SMMU vote clock, then CX (SW_COLLAPSE).

**What to read:**
- `gpu s2a vote …>… gmu_rcg … cfg …>… hub_rcg … rcgfail X`, where 1x is gmu and 2x is hub (x: 2 root stayed off, 3 UPDATE stuck);
- `gpu s2a br gmu …>… cxo … hub … aon … fail mask`;
- `gpu gmu sysreset … fwinit …` and `gpu gmu rsccack …`;
- the banner: `gpu m4 cxon gxoff smmuok gmuR` means the GMU state was read.

**Pass:** `rcgfail 0`, gmu/cxo/hub branches reading CLK_OFF 0, and `sysreset 00000001` (held in reset). `fwinit` and `hfi` read 0. The AO counter should be non-zero and advance between two runs.

**S2b (next):** the GMU cold boot to HFI ready.
- **Firmware:** `gmu_gen70000.bin` must come into the root. This needs a make-ramroot.py copy step from `work/analysis-vendor/stock/vendor_a/firmware/` to e.g. `usr/standalone/firmware/ruan/`, and a root rebuild. It's read with a vnode read on the USB thread.
- **GMU context on the GPU SMMU:** SID 5, banks free, as the SMR survey showed. It needs the ArmSmmu4K kit and the ShengGpuSmmu glue (`refs/unixnu-fuxi/package/ShengGpuSmmu.c`) for page tables.
- **A physically contiguous GMU pool:** amethyst used 32 MiB.
- **ShengGmu's gen7 cold start:** RSC/PDC as in KGSL, ITCM/DTCM load, HFI queues, SYSRESET release, FW_INIT_RESULT poll.
- **Rail vote:** a CX vote through RPMh is probably needed for GX and higher GMU levels, not for HFI-ready at the lowest rate.

## S2a passed; S2b step 1 = `gpu 5` (rbu5)

**S2a result (rbu4):**
- GPLL0 votes `0060257f>0061a57f`.
- gmu_rcg cfg `0>00000602`, hub_rcg cfg `0>00000603`, `rcgfail 0`.
- cx_gmu `221>2f1`; cxo, hub and aon on.
- GMU held in reset: `sysreset 1`, fwinit/hfi 0. `cm3cfg 00004052`, `rpmh 0000000f`, `cxbusy 30000000`, AO counter running (`026f3880`).

**The firmware shows the GMU can't boot from TCM alone.** `gmu_gen70000.bin` has 15 blocks:
- 11 zero-size blocks: preallocation requests, including CACHE-region pages at 0x200, 0x100000, 0x200000 and 0x300000, plus 2 NONCACHED pages at 0x60000000 and 0x60001000 (type 7);
- ITCM 0x0+0x1dc;
- **the main code at GMU VA 0x4000+0xdcac (the CACHE region, i.e. DDR behind the GPU SMMU, SID 5)**;
- DTCM 0x10007f98+0x28 and 0x10007fdc+0x18.

So every boot path needs the SID-5 SMMU context and an SMMU-backed DDR pool first.

**`gpu 5` (rbu5):**
1. Reruns g3 and S2a; both are idempotent.
2. The USB thread reads `/usr/standalone/firmware/ruan/gmu_gen70000.bin` from the root. make-ramroot.py `gpu_firmware()` copies the GMU, SQE and zap files from the local vendor extraction, 0644 root:wheel.
3. Checks the size (57272) and SHA-256 (`b2d3f0e2…`).
4. Validates every block against the gen7 GMU VA map before any write.
5. Only if CM3_SYSRESET reads 1, writes the ITCM and DTCM blocks (127 words) through the GMU window and reads them all back.
- The write allowlist adds only the GMU window's ITCM and DTCM ranges (GMU + 0x5000 .. + 0xd000). The GMU is not started.

**Next, `gpu 6`:**
- the SID-5 context bank (bank 1, SMR slot 2, 4K stage-1 tables), mapping the CACHE preallocations, the 0x4000 code block and the two NONCACHED pages on a pinned contiguous pool;
- the RSC/PDC setup (KGSL `gen7_load_rsc_ucode` and `pdc`) and `power_config`;
- `CM3_SYSRESET` 0;
- poll `FW_INIT_RESULT` bit 8;
- then HFI init.

## gpu 5 passed (rbu5c, 135 TCM words); `gpu 6` = GMU cold boot (rbu6)

`gpu 6` reruns 3, 4 and 5, then:
1. **Pool and tables.** The USB thread allocates a 512 KiB pinned contiguous pool once and never frees it. `RuanGmuMmu.h` builds stage-1 4K tables on it, with T0SZ 32 and Normal NC executable pages, for the 8 GMU regions:
   - the firmware's preallocations: 0x4000+0xe000, 0x100000+0x9000, 0x200000+0x13000, 0x300000+0x7000, 0x60000000 and 0x60001000;
   - HFI at 0x60002000 (16 KiB) and the log at 0x60006000 (16 KiB).
   It copies the 0x4000 code block in, initialises the HFI queue table (UniXNU `AdrenoHfi.c`) and cleans the pool to PoC.
2. **SMMU stream 5.** Refused unless SMR slot 2 is invalid, S2CR 2 is fault (0x20000) and bank 1's SCTLR.M is 0. The bank is at `page*(2^(NUMPAGENDXB+1)+1)` = 0x21000 for ID1 `40000016`.
   - Writes, in arm-smmu order: CBA2R VA64, CBAR (S1, NSH, WB), TCR2 (PA 40), TTBR0 (ASID 1), TCR `00800020`, MAIR0 `44`, then SCTLR M|TRE|AFE|CFRE (no CFIE), TLBIALL plus sync, S2CR = bank 1, SMR = VALID | mask 0x400 | SID 5.
   - **Every write is read back. If any doesn't stick, it reports "refused (hypervisor?)" and reverts.**
3. **Register config**, as KGSL `gen7_gmu_register_config` and `device_start` do: FALNEXT/FAL 1, CX_MISC TCM_RET 1, FW_INIT 0, BOOT_CONFIG 2, QTBL_ADDR 0x60002000, QTBL_INFO 1, AHB_FENCE_RANGE_0, CM3_CFG 0x4052, GBIF_HALT 0, GENERAL_9 0, GENERAL_10 0x07010000, GENERAL_8 log|3, SYS_BUS/ICACHE/DCACHE 1.
4. **Start:** `CM3_SYSRESET 0`, then poll `FW_INIT_RESULT & 0x1ff == 0x100` up to 1000 times, 100 µs apart.
5. **Microcode:** PDC (SEQ_START 0, ENABLE 0x80000001) and the RSC microcode (gen7 generic).
6. **HFI:** `HFI_CTRL_INIT 1`, then poll `HFI_CTRL_STATUS` bit 0 up to 1000 times, 100 µs apart.
7. **Afterwards, pass or fail,** it reads the SMMU fault registers (FSR, FAR, FSYNR0), AO_HOST_INTERRUPT_STATUS and CM3_CFG.

**`gpu off`** now first puts the GMU back in reset (SYSRESET 1), then tears down the context (SMR 0, S2CR fault, SCTLR 0, TLB sync, CBAR/CBA2R 0), then does what it did before.

**Lines to read:**
- `gpu s2c stage N regions 8 pt 65 id1 … cb 21000 smr …>… s2cr …>… cbar …>… sctlr …>… refused 0`
- `gpu s2c booted 1 fwinit 00000100 (… polls) hfi 1 status 00000001 … fsr 00000000 … GMU up, HFI ready`
- banner: `gpu m6 ok s6 fw1 hfi1`

**Stage numbers in the stage field:** 1 = tables, 2 = SMMU, 3 = config, 4 = start, 5 = PDC/RSC, 6 = HFI.

**How to read a failure:**
- `refused 1`: the SMMU is the hypervisor's. Nothing was forced.
- `booted 0` with an `fsr` set: the GMU faulted on the address in `far`, so a mapping is missing.
- `booted 0` with fsr 0: the GMU didn't run its code. Check the GPU/GMU rail votes, or the BOOT_CONFIG and ITCM shadow.
- `hfi 0` after `booted 1`: the queue table or its address.

## rbu6: "no usable GMU pool"; fixed with a reserved GPU pool (rbu6b)

**Why it failed:** IOBufferMemoryDescriptor contiguous allocations only search DarwinBoot's 2.75 GiB window, which the RAM root nearly fills. Adopted outside memory can't serve contiguous allocations. The USB DMA ran into the same thing.

**The fix, the GPU pool 0x8B8B00000 + 16 MiB:**
- **What the range is:** the last 16 MiB of the HLOS bank 0x880000000–0x8B9B00000 in Android's `/memory`. No fixed reserved-memory node lies above 0x800000000; the remaining nodes are dynamic, Linux-placed.
- **Why it's safe:** it sits inside the outside span XNU adopted on rbu6, so it's stage-2 mapped for HLOS and free in the UEFI map. It stays clear of the Gunyah and HYP holes (0x8B9B00000+6M, 0x830000000+256M).
- **How it's kept out of the VM:** board.toml `owned_memory_outside_reserved` gains `"0x8B8B00000:0x1000000"`. DarwinBoot passes it in `/chosen/darwinboot-memory-outside-kept` (present in rbu6b's ADT), and memory-outside skips it.
- **How it's used:** RuanGpuPower.c maps it once with `ml_io_map_unmappable(…, 6 = VM_WIMG_WCOMB)`, Normal non-cacheable, so neither the walker nor the GMU needs cache maintenance, and keeps the mapping for good. **It refuses unless the kept list in the kernel's DT covers the range.** The GMU takes the first 512 KiB; the rest is for later rings, SQE/zap, GPU page tables.
- **USB side:** UsbDebugGpu.h no longer allocates a pool.

## rbu6b froze on a GR1 write; `gpu 7` survey and bank choice (rbu6c)

**rbu6b:** the pool worked, and the stream-5 context writes ran. Some write then failed its readback (the tail of the log doesn't show which), so the teardown ran. **The teardown's GR1 write `CBAR(1) = 0` (SMMU+0x1004) froze the kernel**, even though the earlier read of CBAR(1) and the configuration write to CBAR(1) had gone through.

**Live DT `kgsl-smmu@3da0000`:**
- `qcom,qsmmu-v500, qcom,adreno-smmu`;
- `qcom,skip-init` (set up before us: don't reset the global configuration);
- **`qcom,num-context-banks-override = <6>` and `qcom,num-smr-override = <6>`: HLOS owns banks 0–5 and SMRs 0–5.** The hardware reports 22 and 24; the rest are secure or hypervisor;
- `qcom,actlr = <0x0 0x7ff 0x32b>`; TBUs gfx_0 (SID 0x000–0x3ff) and gfx_1 (SID 0x400–0x7ff);
- GPU `iommus` SID 0 (user) and SID 2 (secure); GMU SID 5, mask 0x400.

adreno-smmu gives bank 0 to the GPU's own stream and allocates other devices from bank 1 up, so bank 1 for the GMU matches Linux.

**Changes:**
- **`gpu 7` (read only, after `gpu 3`):** ID0/ID1, then for banks 0–5 the GR1 CBAR/CBA2R and the bank's SCTLR, TTBR0 and TCR, and SMR/S2CR 0–5. It prints `gpu smmu cbN @offset cbar … | smrN … s2cr …` lines and the chosen free bank and slot.
- **`gpu 6` uses the same survey.** It takes the lowest bank 1–5 with SCTLR.M 0, TTBR0 0 and no valid SMR routed to it (CBAR has no defined reset value, so it's not a test), and the lowest SMR slot 0–5 that is invalid with S2CR fault. The write allowlist only allows that bank and slot, never anything at 6 or above.
- **The teardown no longer writes GR1** (CBAR/CBA2R). With the SMR invalid and SCTLR 0 the bank is unreachable.
- **On a readback mismatch,** the reason now names the first failing register: `SMMU +<off> wrote <v> read <v>: refused?`. Trace labels name `smmu_gr0`, `smmu_gr1` and `smmu_cb` (the old label wrongly said `rbbm`).
